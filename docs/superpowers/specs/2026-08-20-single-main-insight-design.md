# Один главный инсайт объектом content.insight

Дата: 2026-08-20. Статус: одобрено.

## Контекст

После отката кеша профиля инсайты вернулись к легаси-контракту: payload сервиса
нёс массив `content.insights`, auto_insight слал массив из одного элемента, а на
ходах 2+ работала ручная фиксация save_insight с дедупликацией. Сервису нужен
новый контракт: ОДИН главный инсайт объектом `content.insight`, записываемый
один раз — при первом запуске в рамках треда.

## Решение

### Сервис (shared/assignments_service.py)

Заглушка двухрежимная: новый опциональный параметр `insight` (dict) → payload
несёт объект `content.insight`; не передан → легаси-массив `content.insights`
(v1–v3 оркестраторы не тронуты). Форма инсайта прежняя:
`type` / `metric_id` / `metric_name` / `text`.

### auto_insight (первый ход)

Классификация разбора LLM-ом и выбор одного главного (`_first_insight`:
main_problem → norm → первый) не меняются. Отправка — через
`_submit_insight(state, config, ins)` с параметром `insight=`. «Один на тред»
гарантирует топология: auto_insight стоит только в хвосте первого хода.

### save_insight (ходы 2+)

Маршрут интента сохранён, но узел не пишет в сервис и не зовёт LLM: отвечает
`SAVE_INSIGHT_AUTO_FIXED` («главный вывод фиксируется автоматически при старте
разбора»). Старые `SAVE_INSIGHT_DONE/EMPTY/ERROR/NO_SOURCE` удалены.

### Удалённый мёртвый код

`committed_insights` (state), `_drop_committed`, `_insight_key`,
`_gather_agent_answers` (v4), параметр `wish` у `_classify_insights` — вся
дедуп-механика не нужна, запись в сервис происходит один раз.

### Ошибки

Как раньше: сбой сервиса/классификации изолирован (разбор руководитель получает
в любом случае), без `source_type`/`source_id` в сервис не пишем.

## Тесты

`test_insights_v4.py` переработан: payload несёт объект `content.insight` (не
массив), фолбэк на norm, save_insight отвечает «уже зафиксировано» без вызова
сервиса и LLM, двухрежимность заглушки (insight → объект, легаси insights →
массив), изоляция ошибок.
