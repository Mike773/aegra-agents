# Агент-аналитик показателей: как он работает

Верхнеуровневая презентация для бизнеса. Граф `analyst_agent` — чат-ассистент
руководителя, который разбирает показатели команды (план/факт, динамика,
сравнение с коллегами, «звёзды») и опирается на базу знаний (wiki).

---

## 1. Что получает руководитель

- **Диалог в чате.** Руководитель пишет вопрос обычным языком: «как дела у
  команды», «почему просел NPS у Иванова», «кто рискует не получить звезду».
- **Ответ со структурой.** Главная проблема, цифры, причины, сравнение с
  коллегами, рекомендации. Формулировки выдержаны в единой методике.
- **Факты, а не догадки.** Каждая цифра в ответе получена запросом к данным,
  а не придумана моделью. Методика и расшифровка терминов — из корпоративной
  wiki.
- **Опции.** Кнопки с вариантами следующего вопроса, интерактивный график,
  «сигнал» в сервис инсайтов для карточки сотрудника.

---

## 2. Общая картина: один ход диалога

```
 Руководитель ──▶ Вопрос
                    │
   ┌────────────────▼────────────────────────────────────────────┐
   │ 1. Данные        оргструктура → датасет показателей →       │
   │                  предагрегаты по группам коллег              │  первый ход
   │ 2. Подготовка    SQLite ← нормализация ← производные        │  диалога
   │                  поля; трактовки из wiki; карта отклонений   │
   ├─────────────────────────────────────────────────────────────┤
   │ 3. Агент         одна модель + бизнес-промпт + инструменты: │  каждый ход
   │                  SQL-запросы, карточка показателя, коллеги,  │
   │                  рейтинг по звёздам, поиск в wiki            │
   │ 4. Ответ         текст (markdown/HTML), трасса рассуждений,  │
   │                  подсказки, график, сигнал-инсайт            │
   └─────────────────────────────────────────────────────────────┘
```

Данные загружаются и база собирается **один раз на диалог**. Дальше каждый
вопрос — это один проход модели с инструментами по уже готовой базе.

---

## 3. Блок «Структура»: кого и что анализируем

**Вход.** Табельный номер руководителя (и/или сотрудника), должность,
название датасета. Это приходит от клиентского приложения в параметрах запроса.

**Оргструктура.** По табельным номерам сервис оргструктуры определяет:

- кто руководитель и кто его прямые сотрудники;
- `direction_key` — направление бизнеса; по нему изолируются данные и
  знания разных направлений (один агент обслуживает всех, но каждое
  направление видит только своё).

**Датасет показателей.** Сервис датасетов отдаёт по этим фильтрам JSON:
`me` (руководитель) и `employees` (сотрудники). У каждого человека —
**своё дерево показателей**:

```
Сотрудник
 ├─ Показатель 1-го уровня (факт, план, бенчмарк, динамика, ранги)
 │   ├─ дочерний показатель (с весом влияния)
 │   │   └─ ... (разрезы: регионы, продукты, каналы — их бывают сотни)
 │   └─ дочерний показатель
 ├─ Звезда «Лучший по сервису» (получена / не получена)
 │   └─ влияющие на звезду показатели
 └─ Рейтинг по звёздам: место среди коллег по уровням ГОСБ → ТБ → Сбер
```

Важно: состав и вложенность показателей у руководителя и сотрудников могут
различаться, поэтому дерево хранится **на каждого человека**, а общий каталог
показателей — один.

**Предагрегаты.** Для сравнения с коллегами датасет указывает, в каких группах
состоит каждый человек (`aggregates_ids`): отдел, регион, территориальный банк
и т. д. Агент подгружает статистику этих групп (среднее, медиана, квартили,
лучшие значения). Сбой по одной группе не ломает загрузку остальных.

## 4. Блок «Данные wiki»: откуда агент знает методику

База знаний живёт в Postgres (схема `wiki_rag`) и наполняется отдельными
фоновыми графами. Агент-аналитик только **читает** её.

### Как wiki собирается (фон, не на пути ответа)

```
Исходные документы (регламенты, методики, инструкции)
   │  external_doc_loader / doc_manager — загрузка в хранилище source_doc
   ▼
wiki_ingest — чанки → извлечение сущностей моделью → слияние с существующими
              страницами → перекрёстные ссылки → векторы
   ▼
Wiki-страницы и секции с векторами (pgvector) + алиасы/аббревиатуры
   │
   ├─ gap_resolver — пробует закрыть вопросы, на которые wiki не ответила
   └─ metric_enricher — для каждого показателя из каталога ищет трактовку
                        в wiki и кладёт в кэш metric_knowledge
```

### Как агент использует wiki на ходу

1. **Трактовки показателей (кэш).** На первом ходе диалога агент сверяет свой
   каталог показателей с кэшем `metric_knowledge` по данному направлению.
   Недостающие трактовки добирает сам (ограничено числом и таймаутом),
   остальное дособирает фоновый `metric_enricher`. Найденное попадает прямо в
   таблицу показателей в SQLite — значит доступно и промпту, и SQL-запросам
   модели: что означает показатель, как читать его динамику, вид показателя.
2. **Вид показателя** (уровень / вклад / индекс) определяется **всегда**, даже
   без wiki — по названию. Это защищает от бессмысленных процентов: у ранга
   или индекса «отклонение от плана 30 %» не считается.
3. **Поиск по запросу (`search_wiki`).** Когда модели нужна методика или
   расшифровка аббревиатуры, она вызывает подграф `easyrag`:
   сначала точное совпадение по алиасам (аббревиатуры растворяются в
   векторе секции, поэтому у каждого алиаса — свой вектор и точная форма),
   затем векторный поиск по секциям. Wiki — **справка, а не источник чисел**.
4. **Пробелы знаний.** Если wiki не ответила, вопрос записывается как
   `query_gap`; позже его разбирает `gap_resolver`. Так база знаний
   растёт от реальных вопросов руководителей.

## 5. Блок «SQLite»: как данные становятся запрашиваемыми

Вместо того чтобы показывать модели сырой JSON (десятки тысяч строк), агент
собирает **нормализованную базу в памяти** на каждый диалог. Модель пишет к ней
SQL — так же, как аналитик-человек.

### Шаги сборки

```
JSON датасета + предагрегаты
   │
   ▼  Нормализация
   person · metric (каталог) · metric_edge / metric_tree (дерево на человека)
   period · fact · ranking · peer_aggregate · person_peer · rating
   │
   ▼  Производные поля (без модели, детерминированно)
   отклонение от плана и бенчмарка, изменение к прошлому периоду, тренд,
   z-score и место среди коллег, аномалии, «последняя точка серии»
   │
   ▼  Подавление бессмысленных процентов
   у индексов и вкладов относительные отклонения обнуляются
   │
   ▼  Вью с готовыми вердиктами
   v_fact · v_fact_latest · v_tree · v_peer_latest · v_star · v_rating ·
   v_deviation · …
```

### Принципы

- **Даты не связывают показатели.** «Последнее значение» считается на серию
  (человек × показатель × разрез). Если дочерний показатель отстаёт по дате
  от родителя, он не теряется, а показывается со своей датой.
- **Разрезов бывают сотни.** В промпт идут только их число и наличие
  собственного итога; конкретные разрезы модель смотрит инструментами.
  Итог по разрезам **не вычисляется**: складывать проценты и ранги нельзя.
- **Безопасность на стороне базы.** SQL от модели выполняется под защитой:
  база открыта только на чтение, разрешены только SELECT, ограничены число
  строк, колонок, размер ячейки и время запроса. Ни один запрос модели не
  может ничего изменить.
- **Воспроизводимость.** Типовые запросы лежат файлами `.sql` с машинной
  шапкой; те же файлы использует агент, обогащение промпта и отладочный CLI.
  Любой прод-запрос воспроизводится дословно.

## 6. Блок «Карта отклонений»: что важно, решает код

До того как модель начнёт работать, код строит **карту отклонений** по
последним значениям всех серий:

| Вид отклонения | Пример |
|---|---|
| Негативные | хуже плана, ухудшается, аномалия на фоне коллег, хуже коллег, хуже своей группы, отстаёт от сильнейших, звезда не получена, влияющий на звезду показатель ниже плана, худший разрез, по задаче руководителя |
| Позитивные | лучше плана, улучшается, лучше коллег, звезда получена, лучший разрез |

Приоритет каждого отклонения = **влияние × масштаб × управляемость**.

- Верх карты попадает в системный промпт как «Зоны внимания», полная карта
  доступна инструментом.
- Разрезы объясняют показатель, а не конкурируют с ним: разрез попадает в
  карту, только если заметно хуже своего агрегата, и не больше двух на
  показатель.
- **Задачи руководителя** из первого сообщения (нумерованные и маркированные
  строки) разбираются без модели и смещают фокус: показатели задач
  поднимаются, остальные приглушаются, недостигнутая числовая цель становится
  отдельным поводом.
- Карта живёт весь диалог: каждый ход сливается с предыдущей, заметки модели
  сохраняются, исчезнувшие проблемы помечаются решёнными.
- **Главный вывод для сервиса инсайтов** берётся с вершины карты
  детерминированно, без отдельного вызова модели.

## 7. Блок «Агент»: один цикл модели на ход

Архитектурный выбор: **нет роутера, нет отдельного сбора фактов, нет стадии
пересказа**. Одна модель с бизнес-промптом и инструментами сама собирает данные
и сама пишет ответ. Правила формулировок живут в одном месте — в промпте.

### Системный промпт собирается из блоков

```
Бизнес-промпт (роль, принципы анализа, стиль, структура отчёта)
 → Гид по инструментам (сквозные правила)
 → [Подсказки]  [График]                          — только с флагами
 → Состав данных: строка на человека — роль, должность, показатели
   1-го уровня, даты периодов, группы сравнения
 → Зоны внимания (верх карты отклонений)
 → Скорборд показателей верхнего уровня, пробелы данных
 → Память и заметки прошлых ходов
 → [Брифинг]                                      — только где нет истории
 → [Как говорить про звёзды]                      — только если звёзды есть
```

Схема базы **не** лежит в промпте: она — описание инструмента `query_sql`,
примеры запросов — его few-shot. Бизнес-заказчик может заменить бизнес-промпт
параметром, не трогая операционные блоки.

### Инструменты модели

| Инструмент | Что даёт |
|---|---|
| `query_sql` | свободный SELECT по документированной схеме, с указанием цели запроса |
| `metric_card` | всё об одном показателе в одном вызове: периоды, худшие разрезы, состав с весами, коллеги, справка из wiki |
| `peer_context` | группы сравнения от узкой к широкой |
| `star_rating` | место среди коллег по уровням за квартал |
| `search_wiki` | методика и расшифровка терминов |
| `list_deviations` | полная карта отклонений |
| `note_deviation` | зафиксировать находку на будущие ходы |
| `suggest_followups` | варианты следующего вопроса (кнопки) — по флагу |
| `build_chart` | график plotly по данным инструментов — по флагу |

Набор зависит от флагов и данных: нет агрегатов — нет `peer_context`, нет
звёзд — нет `star_rating`, нет wiki — нет `search_wiki`.

### Защиты цикла

- Бюджет вызовов инструментов, лимит объёма выдачи, детектор повторяющихся
  вызовов.
- Каждый вызов инструмента — один шаг, видимый клиенту как сообщение
  прогресса и попадающий в трассу рассуждений.
- **Одна сессия GigaChat на ход**: повторяющийся префикс контекста (промпт,
  история, результаты инструментов) отдаётся из кэша провайдера. Замеры на
  реальных диалогах — 77–86 % токенов из кэша, что прямо снижает стоимость хода.

## 8. Режимы работы

**Обычный ход.** Вопрос → цикл агента → ответ. На ходах 2+ данные не
перезагружаются, история диалога — контекст модели.

**Составной разбор (`dashboard_mode`).** Для широкого брифинга: модель-
планировщик раскладывает брифинг на задачи (до 8), агент решает их по одной
(каждая следующая видит результаты предыдущих), отдельный шаг сводит всё в
один ответ. Подходит для «дай полную картину по команде».

**Сигнальный режим (`run_mode=signal`).** Для автоматических проверок: ответ
дополняется записью в сервис инсайтов — главный вывод, факт и план по метрике,
признак «есть проблема относительно запроса» и текст ответа. Карточка
сотрудника получает сигнал без участия человека.

---

## 9. Контракт с клиентским приложением

- **Шаговые сообщения** во время работы (что сейчас делает агент) и **итоговое
  сообщение** всегда последним.
- Ответ в HTML (по умолчанию) с исходным markdown рядом.
- **Трасса рассуждений** (`reasoning_trace`) и раздел «как получен ответ»
  (`describe_answer`) — для прозрачности и разбора претензий.
- **Подсказки** — до трёх кнопок `{подпись, полный вопрос}`.
- **График** — одна фигура plotly `{data, layout}` с заголовком от модели.
- Все эти блоки включаются флагами; с выключенным флагом контракт не меняется.

## 10. Что это даёт бизнесу

| Было (v4 + отдельный анализатор) | Стало (`analyst_agent`) |
|---|---|
| Несколько LLM-стадий: роутер, сбор фактов, пересказ | Одна модель, один цикл на ход |
| Правила формулировок размазаны по стадиям | Один бизнес-промпт, заменяемый параметром |
| Типизированные инструменты на каждый вопрос | Свободный SQL по нормализованной базе + широкие инструменты |
| Отдельный LLM-вызов для выбора главного инсайта | Детерминированная карта отклонений |
| Полный контекст в каждом вызове | Кэш префикса провайдера, 77–86 % экономии токенов хода |

Контроль качества: около 500 автотестов без сети и без ключей, включая
построчную сверку формул с прежним анализатором на всех эталонных датасетах,
E2E-прогоны на живом GigaChat, отладочный CLI для воспроизведения любого
SQL-запроса из прода.

---

## 11. Границы и честные оговорки

- Модель пишет SQL сама: качество ответа зависит от качества промпта, схемы и
  few-shot примеров. База защищена от любых изменений, но неудачный запрос
  возможен — на это есть подсказки об ошибках и бюджет попыток.
- Трактовки показателей ограничены тем, что есть в wiki. Пробелы фиксируются и
  закрываются фоном, но не мгновенно.
- Числа в ответе берутся только из инструментов; wiki — справка, не источник
  цифр. Это правило промпта, его соблюдение проверяется трассой.
- Сравнение с коллегами доступно только там, где датасет указывает группы
  агрегации.
