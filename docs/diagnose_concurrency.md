# Диагностика: «второй залп из 30 запросов виснет»

Цель — инструментально показать, какой разделяемый ресурс выедается и не
освобождается, когда второй залп встаёт. Ничего не чиним, только наблюдаем.

## ⚠️ Главный подозреваемый по итогам in-process прогона: rate-limit GigaChat (429)

Прогон `scripts/loadtest_inprocess.py --concurrency 6 --batches 2` (in-process,
без HTTP-сервера aegra) показал: уже на **6 одновременных** запросах GigaChat
отдаёт **HTTP 429 RateLimitError** на 5 из 6 (залп #1) и 4 из 6 (залп #2).
Аккаунт GigaChat имеет низкий лимит одновременных запросов/RPS — 30 параллельных
оркестраторов гарантированно его пробивают.

Почему это даёт «второй залп виснет и не оживает» (по коду SDK,
`gigachat/retry.py` + `settings.py`):
- 429/500/502/503/504 входят в `retry_on_status_codes` по умолчанию;
- ретрай делает **блокирующий `time.sleep`** на `retry_after` секунд (а иначе —
  экспонента с потолком 60с). `llm.invoke` живёт в потоке (to_thread/sync-узел),
  значит при `max_retries>0` каждый throttled-вызов **держит поток в sleep до
  60с** → пул потоков (14 на воркер) выедается → второй залп не получает поток.
- При `max_retries=0` (дефолт SDK) 429 сразу падает ошибкой (так было локально),
  без зависания — значит если в проде именно «висит», скорее всего `max_retries`
  где-то поднят, либо квота душит так, что раны копятся.

Что проверить в проде в первую очередь:
1. `py-spy dump` на зависшем воркере — потоки в `time.sleep` (retry-backoff) или
   в `socket.recv`/`ssl` (ждут GigaChat)? Первое = подтверждение этого сценария.
2. Значение `max_retries` GigaChat в конфиге/окружении прода.
3. Квота аккаунта GigaChat (одновременные/RPS) против пиковой нагрузки.
4. Греп логов прода на `429` / `RateLimitError`.

Прим.: полноценный прод-сценарий (HTTP-сервер aegra, 30×30) локально не
воспроизводится — в этом venv нет `uvicorn`/`langgraph_executor.plugins.app`
(их даёт рантайм aegra), а локальная квота GigaChat упирается в ~6. Для точного
повтора нужна прод-квота GigaChat либо мок LLM.

## Итог расследования (что исключено, что осталось)

Симптом уточнён пользователем: 2-й залп **виснет навсегда** (никогда не оживает),
CPU≈0, воспроизводится и на Mac, при этом работает **полный** путь
(json_analyzer + эмбеддинги). «Никогда не оживает» при наличии таймаутов (чат 30с,
эмбеддинги 600с) = ожидание **без таймаута** (lock/семафор), а не медленность.

Проверки на моке (без сети):
- **30×30, лёгкий путь** — оба залпа 30/30, без зависаний (пул `to_thread`
  упирался в 14/14 с очередью, но всегда разгребался).
- **30×2, ПОЛНЫЙ путь** (непустой датасет → реально работает вложенный
  `agent.stream()` json_analyzer внутри `to_thread`) — снова 30/30 и 30/30,
  пик `exec[asyncio] 14/14 queued=30`, до 15 параллельных langgraph-executor'ов,
  но **дедлока нет**: вложенный sync-граф крутится в СВОЁМ per-run executor, а не
  в общем пуле, кольцевой starvation не возникает.

Вывод: **структурный/threading-дедлок исключён.** Раз без сети не виснет даже на
полном пути, а с реальным GigaChat виснет навсегда — причина в **сетевом слое
GigaChat** (ожидание без эффективного таймаута). Единственное такое место в SDK —
`threading.RLock` рефреша токена (`gigachat/client.py:360`, `_sync_token_lock`,
acquire без таймаута) у singleton-клиента; вторично — семафор пула httpx.
Локально подтвердить нельзя: наша тестовая квота режет 429 уже на ~3 параллельных,
до 30 не дойти (429 ≠ вис, падает сразу ошибкой при `max_retries=0`).

**Следующий шаг — снять дамп стеков с РЕАЛЬНО зависшего процесса** (прод или Mac,
где воспроизводится). Инструмент готов и проверен (показывает точные кадры
зажатых потоков):
```
DIAG=1 DIAG_DUMP_EVERY=10 <запуск сервиса/нагрузки>
# когда 2-й залп завис — в stderr раз в 10с печатаются стеки ВСЕХ потоков.
# Резерв: kill -USR1 <pid> (ручной дамп; на macOS может не сработать — тогда авто-дамп).
```
В дампе ищем, на чём стоят зависшие потоки:
- `_sync_token_lock`/`threading`/`lock acquire` → дедлок на рефреше токена GigaChat;
- `httpx`/`_pool`/`semaphore`/`connection` → исчерпание пула коннектов;
- `socket.recv`/`ssl` → ждут ответа GigaChat (тогда проверить, почему не бьёт таймаут).

## Результаты мок-прогона 30×30 (обход квоты)

Мок LLM (`langgraph_executor/mock_llm.py`, подкласс GigaChat без сети, задержка
`MOCK_LLM_LATENCY=2с`) + `scripts/loadtest_inprocess.py --concurrency 30
--batches 2`. Запуск: `MOCK_LLM=1 MOCK_LLM_LATENCY=2 DIAG=1 .venv/bin/python
scripts/loadtest_inprocess.py --concurrency 30 --batches 2`.

Итог:
```
Залп #1: за 10.6с | ok=30 timeout=0 error=0 | ok avg=8.1с (min 6.6 / max 10.6)
Залп #2: за 10.5с | ok=30 timeout=0 error=0 | ok avg=8.0с (min 6.5 / max 10.5)
DIAG пик: exec[asyncio] threads=14/14 queued=16  (24 из 38 семплов)
          Checked out connections: 0
```

Выводы:
1. **Без квоты GigaChat оба залпа 30 проходят целиком** (ok=30/30, без timeout).
   Значит первопричина прод-симптома «второй залп виснет» — именно rate-limit
   429 (+ вероятный блокирующий retry-sleep), а не дедлок в нашем коде.
2. **Подтверждён структурный вторичный боттлнек:** общий `to_thread`-пул
   (`exec[asyncio]`, размер `min(32,cpu+4)`=14) **залипает на 14/14 с очередью 16**
   почти весь прогон — уже при 2 LLM-вызовах на запрос. Каждый
   `asyncio.to_thread(llm.invoke)` всех узлов и tool-loop json_analyzer конкурирует
   здесь. Латентность запроса раздулась с ~4с работы до ~8с (×2) только из-за
   ожидания в очереди пула. В проде с реальным json_analyzer (много вызовов на
   запрос) и реальной задержкой LLM это раздувание умножается → выглядит как
   «висит», даже без 429.
3. БД-пул в этом пути не нагружался (`Checked out: 0`) — на stub-датасете
   (`shared/agent_dataset.py` отдаёт `rows: []`) тяжёлая ветка easyrag/pgvector
   не раскрылась; для нагрузки БД нужен непустой датасет.

Практический вывод для фиксов (отдельным заходом): (а) убрать rate-limit как
стоп-фактор — ограничить конкуренцию к GigaChat семафором + выставить `timeout`
и осознанный `max_retries`; (б) развести нагрузку с дефолтного 14-слотового
пула — перейти на нативный `await llm.ainvoke` вместо `to_thread(llm.invoke)`
либо дать отдельный больший executor.

## Исходные три гипотезы (thread-pool / БД / hung HTTP)

Три гипотезы (ранжированы): (1) исчерпан дефолтный thread-pool loop'а
(`min(32, cpu+4)`; на этой машине = **14** на воркер — его делят sync-узлы
LangGraph route/respond и все `asyncio.to_thread`); (2) исчерпан общий БД-пул
(чекпойнтер aegra + `session_scope` easyrag); (3) зависший HTTP к GigaChat
(нет таймаута / лок на refresh токена) держит поток «вечно».

## Подготовка (один раз)

```bash
.venv/bin/pip install py-spy        # решающий инструмент; на macOS dump требует sudo
```

## Шаг 0 — поднять сервис с диагностикой

```bash
DIAG=1 PYTHONASYNCIODEBUG=1 \
  .venv/bin/uvicorn langgraph_executor.plugins.app:app --workers 2
```

- `DIAG=1` — раз в секунду в лог идёт строка `DIAG | threads ... | exec[...] threads=N/MAX queued=Q | db_pool: ... Checked out: C` (см. `langgraph_executor/diag.py`). Период — `DIAG_INTERVAL=0.5`.
- `PYTHONASYNCIODEBUG=1` — asyncio залогирует колбэки, держащие event loop дольше ~100 мс (остаточная синхронная работа на loop'е).
- Плюс под `DIAG=1` каждый `llm.invoke/ainvoke` пишет `LLM invoke start/end ... dt=Xs` — «вечные» вызовы видно как start без парного end или с огромным dt.

## Шаг 1 — воспроизвести нагрузку (соседний терминал)

```bash
.venv/bin/python scripts/loadtest_orchestrator.py --batches 2 --concurrency 30
```

Печатает по каждому залпу `ok / timeout / error` и тайминги. Симптом
подтверждён, если в залпе #2 много `timeout` (это и есть висящие раны).

## Шаг 2 — py-spy в момент зависания (решает, какая гипотеза)

```bash
pgrep -f "uvicorn .*plugins.app"          # два PID воркеров
sudo py-spy dump --pid <PID>              # стек ВСЕХ потоков воркера
sudo py-spy top  --pid <PID>              # где реально проводится время
```

Чтение дампа:
- все рабочие потоки в `httpx`/`ssl`/`socket.recv` (GigaChat), корутины ждут на `run_in_executor`/`to_thread` → **гип. 1** (или 3, если потоки стоят так дольше таймаута);
- потоки в `_sync_token_lock`/`threading.Lock.acquire` → **гип. 3** (сериализация на refresh токена);
- главный поток в `asyncpg`/ожидании пула, рабочие потоки свободны → **гип. 2**.

Сверить с `DIAG`-логом на момент зависания: `exec[...] queued=Q` растёт при
`threads==MAX` → нехватка потоков (гип. 1); `db_pool Checked out` упёрт в
размер пула → гип. 2.

## Шаг 3 — сторона Postgres (на локальном воспроизведении)

```sql
SELECT count(*), state, wait_event_type, wait_event
FROM pg_stat_activity
GROUP BY state, wait_event_type, wait_event
ORDER BY 1 DESC;
```

Много `idle in transaction` → коннекты держатся внутри узлов дольше нужного
(гип. 2). Число коннектов = размеру пула без движения → пул исчерпан.

## Шаг 4 — изолирующие прогоны (подтверждение «от обратного»)

По одному переключателю за раз, повторяя Шаг 1. Это диагностика, не фиксы:
- **Шире thread-pool**: на старте процесса
  `loop.set_default_executor(ThreadPoolExecutor(max_workers=64))` → ожил 2-й залп ⇒ гип. 1.
- **Таймаут GigaChat**: `timeout=15` в `shared/clients.py` (поле есть в SDK) →
  вместо вечного зависания пошли ошибки и сервис ожил ⇒ гип. 3.
- **Шире БД-пул**: на стороне конфигурации aegra (или fallback-engine в
  `easyrag/db.py`) → ожил ⇒ гип. 2.

Причина найдена, когда py-spy/DIAG-счётчики показывают конкретный
исчерпанный ресурс И расширение **именно его** в Шаге 4 восстанавливает 2-й
залп, а расширение остальных — нет.

## Откат диагностики

Инструментация не активна без `DIAG=1`. Полностью убрать: вызов `start_diag()`
в `link.py`, `wrap_llm_timing(...)` в `shared/clients.py`, файл
`langgraph_executor/diag.py` и `scripts/loadtest_orchestrator.py`.
