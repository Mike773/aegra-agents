# Граф `analyst_agent`

Агент-аналитик показателей: один граф, один бизнес-промпт, немного широких
инструментов. Заменяет связку `analytic_orchestrator_v4` + `json_analyzer_v5`
(они пока остаются в дереве и зарегистрированы).

## Ключевые идеи

- **Один цикл модели на ход.** Роутера-модели, отдельного сбора фактов и стадии
  пересказа нет. Модель с бизнес-промптом и инструментами сама собирает данные и
  сама пишет финальный ответ руководителю. Правила формулировок живут в одном
  месте — в промпте.
- **Модель пишет SQL.** Основной инструмент — `query_sql`: обычный SELECT по
  документированной схеме. Схема (вью, колонки, правила SQLite) лежит в
  описании самого инструмента, примеры запросов — в его `few_shot_examples`;
  в системном промпте схемы нет. Безопасность на стороне базы, а не промпта.
- **Данные нормализованы.** Люди, каталог показателей, структура дерева, факты,
  ранги и предагрегаты лежат в отдельных таблицах in-memory SQLite; агент
  работает через вью с готовыми вердиктами.
- **Карта отклонений вместо обзорных инструментов.** Что важно, считается кодом
  до вызова модели и кладётся в промпт; полная карта доступна инструментом.
- **Даты не связывают показатели.** «Последнее значение» считается на серию
  (человек × показатель × разрез). Дочерний показатель с отстающей датой не
  теряется, а дерево строится только из структуры JSON.
- **Дерево у каждого человека своё.** Состав и вложенность показателей у
  руководителя и сотрудников могут отличаться, поэтому рёбра и позиция
  показателя (`metric_edge`, `metric_tree`) привязаны к человеку; каталог
  `metric` общий, на нём — сводное дерево по всем людям.
- **Разрезов бывают сотни.** В промпт идут только их число и признак наличия
  собственного итога; имена — через инструменты и SQL.

## Топология

```
START ──need_load──▶ load_data ─▶ prepare ─┬─▶ plan_tasks ─▶ agent
      └─(уже загружено)─▶ begin_turn ──────────────────┴─▶ agent
                                                              │
                       agent ─┬─(ещё есть задачи)─▶ agent ────┘
                              ├─(задачи кончились)─▶ summarize ─▶ auto_insight ─▶ END
                              ├─(первый ход)───────▶ auto_insight ─▶ END
                              └─(ход 2+)───────────▶ END
```

Ход turn-based, без `interrupt()`: один вызов графа = одно входящее сообщение →
ответ → END. Состояние между ходами держит чекпойнтер aegra по `thread_id`.

| Узел | LLM | Что делает |
|---|---|---|
| `load_data` | нет | оргструктура, датасет, предагрегаты по `aggregates_ids` (через `shared/offload`) |
| `prepare` | нет* | собирает базу, обогащение промпта, трактовки из wiki, карту отклонений, задачи из брифинга |
| `begin_turn` | нет | ход 2+: сбрасывает то, что живёт один ход |
| `plan_tasks` | 1 | только `dashboard_mode`: брифинг → список задач |
| `agent` | 1 цикл | единственный цикл инструментов; в составном разборе — одна задача за вызов |
| `summarize` | 1 | сводит результаты задач в один ответ |
| `auto_insight` | только в `run_mode=signal` | пишет главный вывод в сервис инсайтов |

\* `prepare` может сделать несколько служебных вызовов модели при холодном кэше
трактовок показателей (ограничены числом и таймаутом).

## Инструменты

| Инструмент | Назначение |
|---|---|
| `query_sql(sql, purpose)` | свободный read-only SELECT; `purpose` идёт в шаг и трассу |
| `metric_card(metric, person, date, depth, element)` | всё об одном показателе: периоды, худшие разрезы, состав с весами, коллеги, справка; с `element` — ряд одного разреза |
| `peer_context(metric, person)` | группы сравнения от узкой к широкой |
| `star_rating(person, quarter)` | рейтинг по звёздам: место среди коллег по уровням (ГОСБ → ТБ → Сбер) за квартал |
| `search_wiki(query)` | методика и расшифровка аббревиатур (справка, не источник чисел) |
| `list_deviations(scope, metric)` | полная карта отклонений |
| `note_deviation(metric, kind, text)` | зафиксировать свою находку на будущие ходы |

Набор зависит от флагов: без `text2sql_enabled` нет `query_sql`, без агрегатов —
`peer_context`, без `easyrag_enabled` — `search_wiki`, без рейтинга —
`star_rating`.

## Данные (`db/`)

Схема — `db/sql/schema.sql`: `person`, `metric` (каталог + трактовки `kn_*`),
`metric_edge` и `metric_tree` (рёбра и место показателя в дереве — на каждого
человека), `period`, `fact`, `fact_analytics`, `ranking`, `peer_aggregate`,
`person_peer`, `rating`, `deviation`. Агент ходит во вью: `v_fact` (главная;
`depth`, `path`, `parent_name` — из дерева этого человека), `v_fact_latest`
(последнее значение каждой серии), `v_series`, `v_metric`, `v_tree` (с
`person_key`), `v_peer_latest`, `v_star`, `v_star_metric`, `v_rating`,
`v_element`, `v_deviation`.

Звёзды: `v_star` — одна строка на (человек, звезда) за последнюю дату серии.
Колонка `metrics` — влияющие показатели одной строкой («имя: факт X при плане
Y, выполнение Z %, вердикт; …»). Влияющие — только дети звезды в дереве этого
человека с признаком `is_star_metric`; обычные показатели рядом со звездой
(например, «Количество оценок») в неё не попадают. Построчно те же показатели
даёт `v_star_metric`.

Рейтинг по звёздам: поле `rating` на персоне (`[{year, quarter, level, place,
staff}]`) — место сотрудника среди коллег уровня за квартал. Приходит только
вместе со звёздами, поэтому и грузится только в базу со звёздами: без них
таблица `rating` пуста, инструмент `star_rating` не привязывается, блок промпта
и справка схемы не меняются. В самом рейтинге уровни — коды (`GOSB`, `TB`,
`SBER`); названия и порядок уровней берутся из агрегатов по коду
(`peer_aggregate.level_name`/`level_order`), без агрегатов имя = код, порядок —
по размеру группы. `v_rating` — строка на (человек, уровень, квартал),
`is_latest` — последний квартал этого человека. В блоке звёзд промпта — одна
строка с местами за последний квартал; история — в инструменте.

`build_run_db(...)` отдаёт готовую базу: загрузка → производные поля
(`analytics.compute_analytics`, построчный порт формул из `json_analyzer_v5`) →
подавление относительных процентов у показателей-«индексов» и «вкладов».

Типовые запросы — файлы `db/sql/*.sql` с машинной шапкой:

```sql
-- name: tool_metric_history
-- params: person_key:str, metric:str, element:str? = NULL, row_limit:int = 60
-- returns: date, fact, plan, plan_status
-- render: table
```

Их гоняют инструменты, обогащение промпта и отладочный CLI — один и тот же файл,
поэтому прод-запрос воспроизводится дословно:

```bash
python scripts/sql_debug.py --dataset samples_v2/sample_declining.json --list
python scripts/sql_debug.py --db dump.db --template tool_metric_history \
    --param person_key=4032085 --param metric=AHT
python scripts/sql_debug.py --dataset samples_v2/sample_star.json --enrichment
```

## Разрезы (элементы)

Разрезов у показателя на проде сотни, поэтому их имена в общий промпт не идут.
В описании показателя (каталог и шапка карточки) даются два факта: **сколько
разрезов** и **есть ли собственный итог** — строка с `element IS NULL`.

- Оба факта считаются **на человека** (`v_metric_person`): у руководителя итог
  может быть, а у сотрудника тот же показатель представлен только разрезами.
  Глобальный флаг увёл бы запрос в `element IS NULL` и скрыл данные сотрудника.
- Если собственного итога нет, показатель не исчезает: в скорборде он идёт
  строкой «только разрезы: N, своего итога нет, хуже плана K, худший разрез — …».
  **Итог не вычисляется** — складывать проценты, средние и ранги бессмысленно, и
  правила промпта прямо это запрещают.
- В карте отклонений разрез объясняет показатель, а не конкурирует с ним:
  сперва отбираются агрегатные отклонения, затем разрезы с капом на показатель
  (`rules.MAX_ELEMENT_DEVS_PER_METRIC`); в блок промпта попадает не более
  четырёх строк-разрезов, по одной на показатель.
- Разрез попадает в карту, только если он **заметно хуже своего агрегата**;
  сам факт проблемного агрегата все его разрезы больше не пропускает.
- Карточка показывает худшие 8 и лучшие 2 разреза плюс «показаны 10 из 300»;
  конкретный разрез смотрится через `metric_card(element=…)`, поиск по части
  имени — через `query_sql` с `LIKE` и `LIMIT`.

## Карта отклонений

`deviations/builder.py` строит её из последних значений серий по правилам
`deviations/rules.py`: виды отклонений (хуже плана, ухудшается, аномалия, хуже
коллег, звезда не получена и т.д.) и приоритет `влияние × масштаб × управляемость`.
Про разрезы — см. раздел выше: они отбираются после показателей, с капом на
показатель и только если заметно хуже своего агрегата.

Карта живёт весь диалог в стейте, каждый ход материализуется в таблицу
`deviation` и сливается с предыдущей: заметки модели живут, исчезнувшие
авто-записи помечаются resolved. Главный вывод для сервиса инсайтов берётся с её
вершины детерминированно (`deviations/insight.py`), без отдельного LLM-вызова.
Помимо `type`/`metric_id`/`metric_name`/`text` инсайт несёт `fact` и `plan`
метрики — последний срез, по которому сформулирован вывод (в v4 они берутся
из датасета по `metric_id`); у записи «в норме» без метрики они `null`.

Сигнальный режим `configurable.run_mode=signal` (общая логика для обоих
агентов — `shared/insight_signal.py`): к инсайту добавляются `author`
(`"Agent"`), `confirmed` (`true`), `signal` — есть ли проблема относительно
входного запроса — и `signal_description` — markdown-текст ответа агента.
Вердикт `signal` даёт единственный LLM-вызов узла (вопрос + ответ → JSON); при
сбое модели берётся тип инсайта (`main_problem` → `true`). Если карта отклонений
пуста, всё равно уходит запись `type=norm`, `signal=false`; если ответа нет
(данные не загрузились) — не уходит ничего. Без `run_mode` payload прежний.

**Задачи из брифинга.** Нумерованные и маркированные строки первого сообщения
разбираются без модели (`deviations/tasks.py`) и смещают фокус карты: показатели
задач поднимаются в приоритете, остальные приглушаются, невыполненная числовая
цель становится отдельным поводом `task_related`.

## Составной разбор (`dashboard_mode`)

Флаг `configurable.dashboard_mode=true` включает планировщик: брифинг → задачи
(до 8). Дальше узел `agent` отрабатывает по одной задаче, следующая видит
результаты предыдущих (полностью — те, от которых зависит; кратко — остальные),
и `summarize` сводит всё в один ответ. Не удалось разложить запрос — ход идёт
обычным путём. На ходах 2+ составной разбор не перезапускается: результаты задач
остаются контекстом.

## Трактовки показателей из базы знаний

Таблицы `wiki_rag.metric_catalog` и `wiki_rag.metric_knowledge` (миграция
`0003_metric_knowledge.sql`). На первом ходе агент добирает трактовки только для
недостающих показателей (кап и таймаут), остальное дособирает фоновый граф
`metric_enricher`. Найденное ложится в колонки `kn_*` таблицы `metric` — значит
доступно и промпту, и SQL-запросам модели.

Правила надёжности: ничего не нашли → пишем строку `unknown`, чтобы не искать то
же самое каждый запуск; упала модель или база → не пишем ничего. Вид показателя
(уровень/вклад/индекс) определяется по названию всегда, даже без базы знаний.

## Configurable

Ключи и дефолты те же, что у `analytic_orchestrator_v4`: `boss_tabnum`,
`employee_tabnum`, `position`, `dataset_name`, `direction_key`,
`source_type`/`source_id`, `run_mode`, `easyrag_enabled`, `easyrag_top_k`,
`gap_on_unanswered`, `use_peer_aggregates`, `emit_progress_messages`,
`describe_answer`, `answer_html`, `system_prompt_override`, `thread_id`.

Новые: `dashboard_mode`, `text2sql_enabled`, `knowledge_enabled`,
`knowledge_max_new`, `knowledge_timeout`, `tool_budget`, `task_tool_budget`,
`max_tasks`, `debug_dump`. Ключ `format_first_answer` принимается ради
совместимости, но ничего не делает: правила формата первого ответа влиты в промпт.

`system_prompt_override` заменяет только бизнес-промпт — одну переменную
`BUSINESS_PROMPT` в `prompts/business.py` (роль, принципы анализа, стиль,
структура отчёта); операционные блоки — гид по инструментам, данные, карта
отклонений — остаются всегда. Как пользоваться конкретным инструментом,
написано в его description; в гиде — только сквозные правила.

## Контракт сообщений

Как в v4: рабочие узлы кладут шаговые сообщения
(`additional_kwargs.orchestrator_step`), итог помечен `orchestrator_final` и
всегда последний. При `answer_html=true` (по умолчанию) `content` — HTML, а
исходный markdown лежит в `additional_kwargs.orchestrator_markdown`. Шаги цикла
инструментов приходят одним апдейтом по завершении узла; для realtime те же
тексты идут в custom stream.

```bash
.venv/bin/python -m pytest tests/analyst_agent tests/metric_enricher -q

E2E_PEER=1 E2E_TURNS=2 .venv/bin/python scripts/e2e_analyst.py
```

Для `E2E_WIKI=1` (база знаний и кэш трактовок) нужен Postgres со схемой
`wiki_rag` и применённой миграцией 0003.
